gedcom-studio architecture

One background process holds your open GEDCOM files. The terminal shell, the web app on your phone and the desktop app all work through it, so they share one set of edits. Nothing reaches the file on disk until one of them saves.

The shape

Three front ends, one daemon, one file

Why it's built this way

Decisions that shape everything else

one door

Everything goes through the Store

Shell commands run holding its write lock and API reads share its read lock. Its revision number goes up on every change and every save, which is how every front end knows to refresh.

your machine only

No server to host

The daemon runs as you, on your computer. Phones reach it over the local network or Tailscale. There's no cloud copy and no offline sync to reconcile.

shared rules

The apps reuse the shell's rules

Adding, linking and unlinking people run the shell's own commands, so the family rules (when a family is created or removed, which links are refused) live in one place.

nothing lost

Unsaved edits are never dropped

The daemon won't stop while files have unsaved edits unless forced, and a forced or signalled stop writes copies to ~/.gedcom-shell/recovery/.

no dependencies

The core is plain Java

The shell, daemon and web app have no runtime dependencies. The web app is plain HTML, CSS and JavaScript with no build step. Only the desktop app adds a library (FlatLaf).

lossless

The file is a tree first

The parser keeps every line as a generic node, and people and families are views over those nodes. Tags it doesn't understand survive a save untouched.

Following one edit

What happens when you add a graduation date on your phone

  1. The form remembers what it showed

    The edit form is prefilled from the person's JSON. Each event carries a ref like GRAD:0 (the first GRAD line) and its current fields.

  2. The app sends only the change

    POST people/I0/edit with the new date and the value it saw: seen: {date: ""}, set: {date: "dec 1997"}.

  3. Everything is checked before anything is applied

    Under the Store's write lock, every seen value is compared with the file as it is now. If someone changed it meanwhile, the reply is 409 and nothing is applied. A bad date gets 422, also with nothing applied.

  4. The tree changes in memory

    The date line is written under the GRAD record, CHAN is touched, indexes update, and the revision goes up. The file on disk is unchanged.

  5. Everyone else catches up

    The desktop app's long poll returns the new revision. It reloads the page, and an open edit form for that same person shows "changed elsewhere". The shell sees it at its next command.

  6. Someone saves

    Ctrl/⌘-S in an app or save in the shell writes the whole tree back to the file.

Inside the code

Packages, from the bytes up

Maven modules: core builds gedcom-shell.jar (shell, daemon, web app), and desktop builds a shaded jar with the Swing app. Each layer below uses only the layers under it.

desktop/

The Swing app, a client of the daemon: page views, the tree chart, edit dialogs, and a ChangeWatcher that follows the revision.

ged/web

The web app: plain JS modules served by the daemon, a service worker for installing to the home screen, and live updates over the same long poll.

ged.client

Finds the running daemon or starts one, and the attached terminal that sends your shell lines to it.

ged.daemon

HTTP server with token check and lock file, the API, Views (records as JSON), the Workspace of open files, shell sessions.

ged.shell

The shell and one class per command. Also run headless by the API for adds and links.

ged.edit

Forms and edits: PersonForm, FamilyForm, and RecordEdits (event, note and name refs, checked then applied as one plan).

ged.vfs

The filesystem view: people and families as directories, relatives as entries, path resolution.

ged.store

The Store: the lock and revision every front end goes through.

ged.model

Person, Family, Name, dates and calendars; Genealogy holds the indexes and answers relationship questions, cycle-safe.

ged.gedcom

Bytes to text to node tree: encoding detection (UTF-8, UTF-16, ANSEL, Latin-1), CONT/CONC, GEDCOM 5.5 to 7.0.

Small helpers sit beside these: ged.json (a strict JSON reader and writer) and ged.text (ANSI styles and width-aware tables).

Where it can be reached

Three ways in, one token

127.0.0.1:7380

This computer

The default. The shell and desktop app find the daemon through ~/.gedcom-shell/daemon.json and start it if it isn't running.

bind=0.0.0.0

Local network

Opt in through daemon.properties. Plain HTTP works on a trusted network; add your own TLS keystore for HTTPS.

tailscale serve

Tailscale (recommended)

HTTPS from anywhere on your tailnet, with the daemon still bound to this computer only.

Every request needs the token, even from this computer, because a proxy like tailscale serve makes remote requests look local. gedcom-shell daemon pair prints an address that hands the token to a browser. The web app sends it in a header, never a cookie, so other sites can't use it. Photos come from signed addresses so <img> tags work without exposing the token.
